# VM benchmark — 2026-09-27

This report compares complete unordered reuse and transfer workloads. It is not
a push/pop latency benchmark, a proof of lock-freedom, or a claim that these
containers provide the same contract. The two timed runs include every case;
slower results and outliers have not been removed.

## Workloads and contracts

| Name | Ordering | Capacity in these workloads |
|---|---|---|
| `sharded` | LIFO within each shard; no global order | Unbounded |
| `lockfree_lifo` | Global LIFO | Unbounded |
| `mutex_vec_lifo` | Global LIFO | Unbounded; initially reserves the pool size or 1,024 slots |
| `segqueue_fifo` | FIFO | Unbounded segmented queue |
| `arrayqueue_fifo` | FIFO | Pool size for reuse; 1,024 slots for MPMC |

- **Object pool:** 1, 4, or 8 workers each complete 20,000 acquire/return cycles.
  The pool starts with four `usize` values per worker and never grows. One
  throughput unit is one completed cycle, containing a pop and a push.
- **MPMC:** 1, 4, or 8 producers, plus the same number of consumers, each with a
  20,000-item quota. This means 2, 8, or **16 total workers**; the final case is
  oversubscribed relative to the VM quota. One throughput unit is one transferred
  item, containing its production and consumption.
- Shard counts are 1, 4, and 8 respectively. All workers start at a barrier.
  Dispatch is static. Every failed operation yields and retries; an unsuccessful
  sharded scan never creates an extra payload. A full ArrayQueue retries the
  original value. Continuous failure checks a 30-second stall threshold every
  1,024 attempts.
- A timed round includes container construction, prefill, thread creation,
  barrier waits, operations, joining, validation, and container destruction.
  Pool validation checks the complete returned value set. MPMC validates range,
  count, sum, XOR, and final emptiness; those checks are sanity checks, not a
  proof of unique delivery for all inputs or schedules. No shared per-item
  progress counter is used.

The workload deliberately performs no useful work on the `usize` payload. It
measures container and scheduling costs, not real buffer serialization. Node
allocation, queue segmentation, mutex contention, and bounded backpressure all
contribute. Epoch reclamation can run in a later round or case: timing `drop`
does not imply that every retired node is reclaimed in that round. These
measurements do not establish total memory usage, fairness, tail latency, or
NUMA behavior.

## Results

Each cell is the range of the two independent run means (vm-a and vm-b), not a confidence interval. Throughput is elements per round divided by Criterion's mean round duration. Per-run 95% intervals are in [results.csv](2026-09-27-vm/results.csv).

Object pool — million acquire/return cycles per second.

| Container | 1 worker | 4 workers | 8 workers |
|---|---:|---:|---:|
| `sharded` | 18.41–18.77 | 16.14–17.55 | 26.43–28.84 |
| `lockfree_lifo` | 43.83–45.21 | 4.13–4.42 | 3.05–3.09 |
| `mutex_vec_lifo` | 78.68–79.15 | 11.34–13.72 | 13.73–14.82 |
| `segqueue_fifo` | 53.68–59.65 | 58.77–63.08 | 57.16–61.90 |
| `arrayqueue_fifo` | 78.98–81.16 | 8.03–9.50 | 4.69–12.83 |

MPMC — million transferred items per second.

| Container | 1p + 1c (2 threads) | 4p + 4c (8 threads) | 8p + 8c (16 threads) |
|---|---:|---:|---:|
| `sharded` | 9.16–10.21 | 8.84–9.63 | 8.12–8.18 |
| `lockfree_lifo` | 6.16–7.37 | 5.35–5.46 | 3.82–3.99 |
| `mutex_vec_lifo` | 9.78–12.03 | 6.54–6.60 | 5.16–5.70 |
| `segqueue_fifo` | 42.24–45.78 | 69.66–70.80 | 69.41–71.15 |
| `arrayqueue_fifo` | 36.19–39.72 | 17.16–33.59 | 10.94–14.76 |

In these runs, sharding improved the 4- and 8-worker object-pool throughput over
both global LIFO baselines, but `SegQueue` was faster at those worker counts.
With one object-pool worker the sharded implementation was the slowest of these
five containers. In MPMC, both Crossbeam queues were faster than the sharded
stack at every tested worker count. If FIFO is acceptable, those queues deserve
to be measured alongside this crate in a real application.

Some results varied substantially between runs: the 8-worker ArrayQueue pool
case ranged from 4.69 to 12.83 million cycles/s. The data does not isolate why;
bounded-queue contention and VM scheduling are possible contributors, not
established explanations. Two runs do not justify close rankings or a universal
speedup claim.

## Reproduce

Use the repository revision containing this report. Run in a disposable clean
checkout, since the following command installs the archived dependency lockfile
as `Cargo.lock`:

```sh
rustup toolchain install 1.98.1 --profile minimal
cp docs/benchmarks/2026-09-27-vm/Cargo.lock.snapshot Cargo.lock
cargo +1.98.1 bench --locked --bench stack_bench --no-run
cargo +1.98.1 bench --locked --bench stack_bench -- \
  --sample-size 20 --warm-up-time 1 --measurement-time 3 \
  --nresamples 10000 --noplot --save-baseline vm-a
cargo +1.98.1 bench --locked --bench stack_bench -- \
  --sample-size 20 --warm-up-time 1 --measurement-time 3 \
  --nresamples 10000 --noplot --save-baseline vm-b
python3 docs/benchmarks/summarize.py --output-dir target/vm-report
```

The two runs use separate processes and the same fixed case order. Criterion
uses 20 samples, a 1-second warmup and a 3-second target measurement time per
case, with 10,000 bootstrap resamples and 95% confidence intervals. It can extend
the measurement period or change sampling mode to collect enough samples;
see the logs for warnings and actual iteration counts. This is a short VM
experiment with two repetitions, not a claim of statistical generality across
machines. No cases were rerun selectively.

The summary uses **elements per round divided by Criterion's mean round
duration**, with duration confidence-interval endpoints inverted for throughput.
Criterion's console output can use the slope estimator for linear sampling, so
its point estimates can differ from this report. Each table cell spans the two
separate runs' mean-based throughput estimates; it is **not a confidence
interval**. Per-run 95% intervals are in the CSV. No p99 claim is made from these
batch measurements.
